# Вход владельца и защита владельческих операций

## Контекст

Календарь принадлежит одному заранее заданному владельцу, но до этого решения
все операции API были анонимными. Прямой запрос `GET /api/v1/bookings` отдавал
имена и email гостей любому клиенту, а `POST /api/v1/meeting-types` позволял
постороннему менять расписание. Прототип работает на одном экземпляре с
хранилищем в памяти и без внешних провайдеров личности.

## Решение

- **Один общий пароль владельца** в переменной окружения `OWNER_PASSWORD`.
  Учётных записей, ролей, регистрации и восстановления пароля нет: владелец
  календаря ровно один и задан заранее.
- **Подписанная сессионная cookie** `owner_session` со значением
  `v1.<unix-время-истечения>.<hex HMAC-SHA256>`. MAC считается по строке
  `v1.<unix-время-истечения>`. Время жизни — 12 часов без продления при
  активности. Атрибуты: `HttpOnly`, `SameSite=Lax`, `Path=/`; `Secure`
  выставляется, когда запрос пришёл по TLS или с `X-Forwarded-Proto: https`.
- **Ключ подписи** — `OWNER_SESSION_SECRET`, если задан. Иначе ключ
  детерминированно выводится из пароля, чтобы сервис работал после перезапуска
  без второй переменной. Смена пароля или ключа инвалидирует все сессии.
- **Один шов проверки доступа** — middleware вокруг сгенерированного
  HTTP-обработчика. Список владельческих `method + path` задан в одном месте;
  в хендлерах отдельных проверок нет, поэтому новый владельческий маршрут нельзя
  случайно оставить открытым.
- **Граница владения.** Владельческие операции: создание типа встречи в legacy
  и v1 API, список предстоящих записей. Публичные операции: проверка здоровья,
  списки и получение типов встреч, свободные слоты, создание записи, операции
  сессии.
- **Отказ** — `401` с `ApiErrorV1` и кодом `unauthorized`; неверный пароль —
  `401` с кодом `invalid_credentials`. Пароль сравнивается за постоянное время,
  не логируется и не возвращается в ответах.
- **Защита от межсайтовых запросов** опирается на `SameSite=Lax`, JSON-тело и
  проверку `Origin`/`Referer` на сервере для владельческих запросов. Отдельного
  CSRF-токена нет.
- **Демонстрационный режим.** Защита включена тогда и только тогда, когда
  `OWNER_PASSWORD` непустой. Без пароля сервер штатно стартует, владельческие
  операции остаются открытыми, при старте пишется предупреждение, а интерфейс
  показывает пометку демонстрационного режима. Пароля по умолчанию или
  значения-заглушки не существует.

## Последствия

- Прямой `curl` к владельческим операциям теперь требует предварительного входа
  и cookie; это осознанное изменение публичного контракта.
- Сессии хранятся только в подписанной cookie, без серверного хранилища.
  Поэтому выход очищает cookie у клиента, но украденная cookie остаётся
  действительной до истечения срока; отзыв всех сессий выполняется сменой
  пароля или ключа подписи.
- Развёртывание без `OWNER_PASSWORD` остаётся демонстрационным и незащищённым.
  Это нужно явно указывать в README и при развёртывании на Render.
- Ограничение попыток входа, блокировка по адресу, капча, несколько владельцев,
  внешние провайдеры личности и отдельный CSRF-токен остаются вне области этого
  решения.

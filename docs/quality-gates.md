# Проверки качества

Единая команда для локальной разработки и CI — `mise run check`. Она запускает все
проверки, относящиеся к уже появившимся частям приложения. Команда проверки не
исправляет файлы и не меняет рабочее дерево. Отдельные команды форматирования и
генерации могут менять файлы.

После `mise install` выполните `mise exec -- hk install --mise`, чтобы включить Git hooks:
pre-commit проверяет секреты в индексе и изменённые Markdown-файлы, а pre-push
запускает полную команду проверок. CI проверяет историю и рабочее дерево на секреты
и проверяет инструкции агентов через `agnix --strict`.

Внедрение проверок для ещё не написанных частей приложения отслеживается в
[задаче #7](https://github.com/godovdm/ai-for-developers-project-386/issues/7).

## Включение проверок

| Каталог | Условие включения | Обязательные проверки |
| --- | --- | --- |
| Корень проекта | Всегда | Markdown lint; `actionlint` для GitHub workflows |
| `api/` | Каталог существует | Формат TypeSpec и компиляция; Redocly `recommended-strict` для OpenAPI; воспроизводимость сгенерированных OpenAPI, Go API и TypeScript SDK |
| `backend/` | Каталог существует | Формат и импорты Go; строгий `golangci-lint`; сборка; тесты с детектором гонок; `govulncheck` |
| `frontend/` | Каталог существует | Prettier; строгие ESLint и `tsc`; Vitest; production build; `pnpm audit --audit-level high` |
| `backend/` и `frontend/` | Оба каталога существуют | Playwright: вход владельца, создание типа встречи, запись гостя, список владельца и отказ без входа в Chromium, Firefox и WebKit |

Отсутствующий каталог пропускается. Появившийся каталог без манифеста, конфигурации
проверок или тестов приводит к ошибке. Добавление части приложения требует сразу
включить её проверки; пустые задачи и пропуск ошибок не допускаются.

## Строгие профили

Go: `gofmt` и проверка импортов; `golangci-lint` с зафиксированным набором
`govet`, `staticcheck`, `errcheck`, `ineffassign`, `unused`, `revive`, `gocritic`,
`errorlint`, `exhaustive`, `gosec`, `bodyclose`, `noctx` и `nilerr`. Находки
блокируют проверку. Тесты запускаются командой `go test -race -count=1 ./...`.

TypeScript и React: строгие настройки компилятора, включая проверки индексного
доступа и необязательных свойств; `typescript-eslint` с `strictTypeChecked` и
`stylisticTypeChecked`; правила React и React Hooks;
`eslint --max-warnings 0`. Prettier проверяет формат, а `tsc` — типы в
компонентах. Необоснованный `any` запрещён.

TypeSpec: `tsp format --check` и компиляция с правилом
`@azure-tools/typespec-azure-core/casing-style` требуют PascalCase для имён моделей;
предупреждения компилятора считаются ошибками. Redocly `recommended-strict` проверяет сгенерированный OpenAPI. Генераторы
и их версии фиксируются; сравнение с отслеживаемыми файлами учитывает новые файлы
и не меняет рабочее дерево.

Вместо несовместимого с текущим компилятором набора
`@typespec/best-practices/recommended` используется правило именования моделей
Azure Core. Владельческие операции объявляют cookie-аутентификацию
`owner_session` и ответ `401`, поэтому исключение Redocly про отсутствие
авторизации для них не применяется. Для действительно публичных операций
адресно исключаются правила о лицензии, анонимном доступе и ответе 4XX:
лицензия ещё не выбрана, публичные методы работают без входа, а у проверки
здоровья, списка типов встреч и операций сессии нет 4XX-ответа.

Сгенерированные Go и TypeScript файлы исключаются только из правил стиля. Они
остаются в сборке и проверке типов. Подавление отдельного правила допускается
только рядом с кодом и с объяснением; изменение общего набора правил требует
отдельного решения.

## Сценарии тестов

Тесты правил календаря проверяют окно от завтра до четырнадцатого дня в
`Europe/Moscow`, переход через полночь, будни, рабочее время 10:00–18:00,
длительности 30/60/90/120 минут, шаг 30 минут и последний допустимый старт.
Пересечения записей, включая частичные и между разными типами встреч, запрещены;
смежные интервалы допустимы.

HTTP-тесты проверяют создание типа встречи, получение слотов, успешную и
повторную запись, список предстоящих записей владельца и неизменность состояния
после ошибки. В тесте одновременной записи на один слот успешен ровно один запрос.

Отдельные HTTP-тесты проверяют сессию владельца: вход с верным и неверным
паролем, атрибуты и срок cookie, отказ владельческим операциям без сессии,
доступ с сессией, выход, испорченную и просроченную cookie, смену пароля,
`Secure` за TLS-прокси, отказ запросу с чужим `Origin`, публичность гостевых
операций и демонстрационный режим без пароля. Пароль не появляется в ответах и
логах.

Тесты frontend проверяют загрузку списка типов встреч, пустое состояние, ошибку с
повтором, создание типа владельцем, вход на `/owner/login`, сообщение о неверном
пароле, переход на вход без сессии, возврат на вход по `401`, выход и пометку
демонстрационного режима. Playwright проходит путь: владелец входит по паролю с
переменной окружения → создаёт тип встречи → гость выбирает слот и получает
подтверждение → запись появляется в списке владельца; отдельный сценарий
проверяет форму входа и `401` от API без сессии. Для тестов задаётся независимое
начальное состояние; числовой порог покрытия не установлен.

## CI и версии

Новый workflow запускает `mise run check` на pull request и push в `main`.
Его результат становится обязательной проверкой ветки. Существующий Hexlet
workflow не меняется. Версии инструментов фиксируются через `mise.toml` и
`mise.lock`; зависимости JavaScript — через lockfile и `pnpm install --frozen-lockfile`.
